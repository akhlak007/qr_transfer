# Phase 8E End-to-End Software Integration Report

## Verification scope

Phase 8E validates the application software path only. Every result in this report has:

- `verificationType: "SOFTWARE"`
- `channelLabel: "SOFTWARE OPTICAL CHANNEL / SIMULATION"`

These executions are not physical camera/display validation and make no hardware-performance claim.

## Architecture

```text
File bytes
  -> protocol metadata/sequential/fountain framing
  -> explicit QR | VLC OOK | Visual OFDM transmitter pipeline
  -> deterministic SOFTWARE OPTICAL CHANNEL / SIMULATION
  -> matching explicit receiver pipeline (no fallback)
  -> CRC-gated protocol payload dispatch
  -> sequential/fountain reconstruction
  -> exact SHA-256 comparison
```

The application uses a strict pipeline registry. QR calls the existing QR encoder and `scanQRCode`; VLC calls the real VLC framing/modulator and `VlcOokReceiver`; Visual OFDM calls the real OFDM framing/modulator/spatial-grid representation and `VisualOfdmReceiver`.

The live sender scheduler keeps separate application-frame, VLC-symbol, and OFDM-grid counters. A payload cannot advance until all of its optical units have rendered. The live receiver router has no QR fallback and rejects unknown transports explicitly.

## Method

The recorded verification matrix used the deterministic 48-byte payload generated by `(index * 37 + 11) & 0xff`, with expected SHA-256:

`a6250da1e7ca144af7fdac8fd737c2e88e87cc08e232b16b53452227a56d5dde`

The software channel is seeded and can apply luminance/RGB noise, brightness drift, frame drops, optical-unit corruption, and sampling variation. It is a reproducible simulation model, not a claim that camera hardware is reproduced exactly.

## Limitations and non-fabrication statement

The software channel is deliberately deterministic and bounded. It does not model all display, optics, rolling-shutter, camera ISP, autofocus, motion, or environmental effects. No distance, throughput, BER, camera tolerance, or hardware-readiness number is inferred from these runs. A status is promoted to `SOFTWARE_END_TO_END_VERIFIED` only from an executed full-path record; absent or incomplete evidence remains `EXPERIMENTAL` or `FAILED`.
